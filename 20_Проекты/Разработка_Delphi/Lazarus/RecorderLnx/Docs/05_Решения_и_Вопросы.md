## Расположение исходников и тестов

Маркер решения: `RLNX_PATHS_2026_05_22`.

- Основной проект RecorderLnx: `D:\works\OburecGH\Lazarus\RecorderLnx\`.
- Общий код для разных Lazarus-проектов: `D:\works\OburecGH\Lazarus\SharedUtils\`.
- Тесты-примеры RecorderLnx: `D:\works\OburecGH\Lazarus\Tests\RecorderTests\`.

Правило использования `SharedUtils`: перед созданием общего класса проверять существующие units в `SharedUtils`; если класс становится общим для нескольких проектов, переносить его туда только после отделения от доменной логики RecorderLnx.

Правило тестов: каждый новый класс RecorderLnx получает пример в `Tests\RecorderTests`; пример должен быть достаточно понятным, чтобы служить документацией использования.

- Пишем на Lazarus/FPC как нативное приложение.
- Целевая платформа первой версии: Linux.
- UI строится на LCL.
- Ядро не зависит от Windows COM.
- Зависимости допустимы только при наличии исходного кода и понятной лицензии.
- Расширяемость проектируется заранее, но первая реализация может начинаться со статически подключённых модулей, если публичный интерфейс не мешает будущему `.so`.
- Каждый новый класс/ или несколько классов взаимосвязанных сопровождается примером использования/тестом. Иногда стоит нарастить существующий тест а не писать новый. Например, если сделали пример для добавления на наш компонент отрисовки графиков линии и сделали тест пример, то потом когда добавим управление толщиной линии не стоит писать новый пример.
- Все классы и интерфейсы заносятся в проектный реестр, чтобы не дублировать функционал.

## Открытые вопросы

### Механизм внешних модулей

Варианты: `.so` + C ABI; FPC package/runtime loading; отдельные процессы через IPC; скриптовый слой.

Предварительный выбор: `.so` + C ABI для нативных плагинов и, возможно, IPC для тяжёлых/нестабильных обработчиков. Требуется отдельный прототип.

### Формат записи данных

Не решено: нужен ли бинарный формат, совместимый с существующим Recorder/MERA; нужен ли простой открытый формат для первой версии; как хранить метаданные проекта, шкалы, теги, события, версии конфигурации.

### UI формуляров

Не решено: формуляр как `TFrame`, `TForm` или собственный canvas/control; формат хранения мнемосхем; как подключать внешние формуляры без пересборки; какие графические компоненты можно использовать без риска зависимости.

### Источник данных vs устройство

Предварительное разделение: устройство — физическая/логическая сущность конфигурации; источник данных — активный producer данных с `UpdateTime`; один источник может давать несколько тегов; одно устройство может содержать несколько источников.

Нужно проверить на реальных измерительных системах.

### Совместимость с Windows Recorder

Пока переносим функциональные идеи, а не ABI. Отдельно решить: нужны ли конвертеры старых конфигураций; нужны ли совместимые плагины или только новая plugin API; какие свойства `RCPROP_*`, `TAGPROP_*`, `PN_*` обязательны в первой версии.
