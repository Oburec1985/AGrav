## Расположение исходников и тестов

Маркер решения: `RLNX_PATHS_2026_05_22`.

- Основной проект RecorderLnx: `D:\works\OburecGH\Lazarus\RecorderLnx\`.
- Общий код для разных Lazarus-проектов: `D:\works\OburecGH\Lazarus\SharedUtils\`.
- Тесты-примеры RecorderLnx: `D:\works\OburecGH\Lazarus\Tests\RecorderTests\`.

Правило использования `SharedUtils`: перед созданием общего класса проверять существующие units в `SharedUtils`; если класс становится общим для нескольких проектов, переносить его туда только после отделения от доменной логики RecorderLnx.

Правило тестов: каждый новый класс RecorderLnx получает пример в `Tests\RecorderTests`; пример должен быть достаточно понятным, чтобы служить документацией использования.

- Пишем на Lazarus/FPC как нативное приложение.
- Целевые платформы первой версии: Windows и Linux.
- UI строится на LCL.
- Ядро не зависит от Windows COM.
- Зависимости допустимы только при наличии исходного кода и понятной лицензии.
- Расширяемость проектируется заранее, но первая реализация может начинаться со статически подключённых модулей, если публичный интерфейс не мешает будущим `.dll/.so`.
- Каждый новый класс/ или несколько классов взаимосвязанных сопровождается примером использования/тестом. Иногда стоит нарастить существующий тест а не писать новый. Например, если сделали пример для добавления на наш компонент отрисовки графиков линии и сделали тест пример, то потом когда добавим управление толщиной линии не стоит писать новый пример.
- Все классы и интерфейсы заносятся в проектный реестр, чтобы не дублировать функционал.


## Кроссплатформенность Windows/Linux

Маркер решения: `RLNX_CROSS_PLATFORM_2026_05_25`.

RecorderLnx должен собираться и работать и под Windows, и под Linux. Linux остается важной целевой средой эксплуатации, но архитектурные решения, структура проекта, тесты и зависимости не должны без необходимости привязывать ядро к одной ОС.

Платформенно-зависимый код допускается только за тонкими адаптерами с условной компиляцией ``{$IFDEF WINDOWS}`` / ``{$IFDEF UNIX}`` и отдельной записью в карте классов/модулей.


## Руководство пользователя Recorder как источник требований

Маркер решения: `RLNX_RECORDER_MANUAL_2026_05_25`.

Используем `D:\works\AGrav\temp\МЕРА\Recorder\Recorder. Руководство пользователя.pdf` как источник рабочих сценариев и терминов. Интерфейсы Windows Recorder показывают программные контракты, а руководство показывает пользовательскую модель: конфигурация, каналы, формуляры, Preview/Просмотр, Record/Запись, условия старта/остановки, кадр/замер, рабочий каталог, MERA/USML и плагины.

Первое следствие: в ближайшем state machine вместо нейтрального `View` предпочтительно использовать `Preview`, а вопрос ожидания триггера (`Armed/WaitingForTrigger`) вынести на согласование перед кодом.

## Минимальная модель state machine

Маркер решения: `RLNX_STATE_MACHINE_2026_05_25`.

Первая реализация `TRecorderStateMachine` фиксирует рабочие режимы из руководства Recorder без каналов и файлов записи: `Stop`, `PreviewArmed`, `Preview`, `RecordArmed`, `Record`. Суффикс `Armed` означает, что пользователь запросил Preview/Record, но фактический старт ожидает условия: уровень сигнала, внешний цифровой/TTL trigger или время. Ручной старт сразу переводит в `Preview` или `Record`.

Прямой `Stop -> Record` разрешен, потому что в Recorder запись запускается F2; если задано неручное условие старта, переход идет в `RecordArmed`.

## Последовательность разработки

Маркер решения: `RLNX_CORE_FIRST_FLOW_2026_05_25`.

Для RecorderLnx при выборе следующего шага действует порядок: ядро -> минимальный интерфейс наблюдения состояния -> инструменты настройки и тестовые функции-примеры -> сохранение/загрузка конфигурации -> полноценный интерфейс настройки. Минимальный UI наблюдения допускается рано, если он только показывает состояние и вызывает готовые команды ядра; UI настройки остается последним.

## Производительность и аппаратное ускорение

Маркер решения: `RLNX_PERFORMANCE_ACCELERATION_2026_05_25`.

RecorderLnx должен учитывать высокую производительность как архитектурное требование. Тяжелые расчеты, спектры, массовые операции с массивами, копирование больших блоков данных и графика больших потоков должны проектироваться с возможностью аппаратного ускорения.

Существующая точка переиспользования: `D:\works\OburecGH\sharedUtils\math\uHardwareMath.pas`. В нем уже есть aligned memory helpers, SSE/AVX проверки, SSE операции над double-массивами, FFT, спектральные окна и нормализация спектра. Перед созданием новых математических классов RecorderLnx проверять этот unit и решать, нужен ли перенос/адаптер в Lazarus SharedUtils.

OpenGL-графика рассматривается как будущий путь ускоренной визуализации, но после ядра, тестовых примеров и конфигурации.

## Настройки запуска и остановки

Маркер решения: `RLNX_RUN_CONTROL_SETTINGS_2026_05_25`.

Для первой версии ядра настройки запуска/остановки реализуются одним классом `TRecorderRunControlSettings`. Фронт уровня ограничен вариантами `Rising/Falling`. Временной старт/остановка задается задержкой/длительностью в миллисекундах (`DelayMs`), без абсолютного времени. Канал пока задается строкой, уровень — `Double`; привязка к дереву каналов будет добавлена позже.

## Формат конфигурации запуска/остановки

Маркер решения: `RLNX_RUN_CONTROL_CONFIG_2026_05_25`.

Первая конфигурация `TRecorderRunControlSettings` хранится в INI-файле с разделами `Start` и `Stop`. Enum-значения пишутся стабильными строками (`Manual`, `SignalLevel`, `ExternalTrigger`, `Time`, `Duration`, `Rising`, `Falling`). Такой формат выбран как простой, читаемый и близкий к INI-подобным описателям Recorder/MERA. Более общий формат проекта можно пересмотреть позже, когда появятся каналы, дерево устройств и настройки записи.

## Уровни конфигурации

Маркер решения: `RLNX_CONFIG_LEVELS_2026_05_25`.

RecorderLnx различает глобальную настройку программы и конфигурацию проекта. Глобальная настройка хранит список плагинов, дефолтный проектный конфиг, шрифты, тип времени (ПК/UTC) и может выбираться параметрами строки запуска. Конфигурация проекта — это каталог с набором файлов: GUI, настройки плагинов, аппаратная конфигурация, настройки запуска/остановки и будущие формуляры.

Первая dev-структура: `config\app.ini`, `config\projects\default\`, `config\projects\default\run-control.ini`.

## Preview и Record: условия старта

Маркер решения: `RLNX_PREVIEW_RECORD_START_2026_05_25`.

`Preview` запускается только вручную пользователем или внешней программой/плагином. В Stop данные не идут, поэтому проверять триггер или уровень для Preview нельзя. `Record` использует настройки старта из `TRecorderRunControlSettings`: ручной старт начинает запись сразу, неручной старт переводит в `RecordArmed` до события условия.

## Фабрики компонентов формуляров

Маркер решения: `RLNX_FACTORY_MANAGER_2026_05_25`.

В базовом ядре RecorderLnx не переносим пользовательскую надстройку `cCompMng/cRecBasicFactory` напрямую. Берем только паттерн из Recorder: есть менеджер/регистратор фабрик, каждая фабрика отвечает за свой тип компонента, создает дочерние экземпляры и знает их по индексу, а компонент при удалении уведомляет фабрику.

Первая реализация в `uRecorderFormModel.pas`: `TRecorderComponentFactory` выполняет роль менеджера фабрик; `TRecorderComponentFactoryBase` является фабрикой одного типа; `TRecorderStaticTextFactory` и `TRecorderTagValueFactory` регистрируются как базовый набор. Страница формуляра удаляет компоненты через их фабрику, чтобы не появлялись висячие ссылки.
## Открытые вопросы

### Механизм внешних модулей

Варианты: `.dll/.so` + C ABI; FPC package/runtime loading; отдельные процессы через IPC; скриптовый слой.

Предварительный выбор: `.dll/.so` + C ABI для нативных плагинов и, возможно, IPC для тяжёлых/нестабильных обработчиков. Требуется отдельный прототип.

### Формат записи данных

Не решено: нужен ли бинарный формат, совместимый с существующим Recorder/MERA; нужен ли простой открытый формат для первой версии; как хранить метаданные проекта, шкалы, теги, события, версии конфигурации.

### UI формуляров

Не решено: формуляр как `TFrame`, `TForm` или собственный canvas/control; формат хранения мнемосхем; как подключать внешние формуляры без пересборки; какие графические компоненты можно использовать без риска зависимости.

### Источник данных vs устройство

Предварительное разделение: устройство — физическая/логическая сущность конфигурации; источник данных — активный producer данных с `UpdateTime`; один источник может давать несколько тегов; одно устройство может содержать несколько источников.

Нужно проверить на реальных измерительных системах.

### Совместимость с Windows Recorder

Пока переносим функциональные идеи, а не ABI. Отдельно решить: нужны ли конвертеры старых конфигураций; нужны ли совместимые плагины или только новая plugin API; какие свойства `RCPROP_*`, `TAGPROP_*`, `PN_*` обязательны в первой версии.
