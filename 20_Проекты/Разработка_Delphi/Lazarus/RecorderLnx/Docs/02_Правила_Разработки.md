# RecorderLnx: правила разработки

## Главный стиль работы

## Обязательное согласование перед кодом

Маркер правила: `RLNX_COLLAB_BEFORE_CODE`.

В этом проекте перед реализацией любого нового функционала сначала задавать пользователю наводящие вопросы и фиксировать решение. Код писать только после согласования поведения, границ и ожидаемого примера/теста.

Минимальный набор вопросов перед классом или крупным блоком:

- какую задачу решает функционал и кто его будет вызывать;
- какие входы, выходы и ошибки считаются нормальными;
- в каком потоке работает код и кто владеет данными;
- какие существующие классы/интерфейсы надо переиспользовать;
- какой пример использования будет одновременно тестом;
- что записать в карту классов после реализации.

Если пользователь уже дал точное решение, уточняющие вопросы можно сократить, но шаг согласования не пропускать.

Пишем системно и не спешно. Каждый класс или крупный блок проходит цикл: назначение и место в архитектуре, публичный интерфейс, минимальная реализация, пример использования, запись в карту классов/интерфейсов, короткая заметка в `cach/plan.md` или проектной документации.

Если функционал уже есть в проекте, используем его. Если кажется, что надо написать похожий класс, сначала проверяем [Карту интерфейсов](./03_Карта_Интерфейсов.md) и существующие исходники.


## Порядок разработки функционала

Маркер правила: `RLNX_CORE_FIRST_FLOW_2026_05_25`.

Когда возникает выбор, что делать следующим, использовать постоянную последовательность RecorderLnx:

1. Сначала ядро: доменные типы, состояния, алгоритмы, потоки, структуры данных без UI.
2. Затем минимальный интерфейс наблюдения состояния, если он помогает видеть работу ядра: индикатор состояния, журнал событий, простые команды запуска/остановки без полноценной настройки.
3. Потом инструменты настройки и тестовые функции-примеры: один или несколько примеров для проверки разных режимов и демонстрации использования.
4. Потом сохранение/загрузка конфигурации для уже проверенного ядра.
5. Только после этого полноценный визуальный интерфейс настройки, который подключается к готовому ядру и конфигурации.

UI не должен становиться местом, где впервые появляется доменная логика. Минимальный интерфейс наблюдения состояния допускается рано, но он только показывает состояние и дергает готовые команды ядра. Если для UI настройки не хватает модели или конфигурации, сначала возвращаемся к ядру/примеру/сериализации.



## Безопасное обновление файлов

Маркер правила: `RLNX_FILE_UPDATE_SAFETY_2026_05_25`.

При работе с Lazarus-проектом нельзя полагаться только на факт успешного патча или сборки: IDE может создавать `backup\`, а при копировании из backup можно случайно оставить старое время изменения или перетереть новую версию старой.

Правила обновления исходников:

- редактировать только рабочий файл проекта, а не `backup\`, `lib\`, `__history\` или сгенерированные копии;
- после правки проверять рабочий файл по полному пути: наличие ключевых строк/методов, размер и `LastWriteTime`;
- если восстановление делалось из backup или копированием, обновить `LastWriteTime` рабочего файла текущим временем, чтобы Lazarus предложил перечитать файл;
- перед финальным ответом для измененных units выполнять принудительную сборку (`lazbuild -B` или `fpc -B` для теста), когда есть риск устаревших `.ppu`/`.o`;
- при подозрении на дубликаты искать файл по всему дереву проекта и сверять рабочую версию с backup;
- не считать backup источником истины: источник истины — рабочий файл в `D:\works\OburecGH\Lazarus\RecorderLnx\...` плюс проходящий тест/сборка.

Если пользователь говорит, что Lazarus не предложил перечитать файл, первым делом проверять `LastWriteTime`, наличие дубликатов и принудительно компилировать с `-B`.
## Производительность и аппаратное ускорение

Маркер правила: `RLNX_PERFORMANCE_ACCELERATION_2026_05_25`.

RecorderLnx проектируется как высокопроизводительное приложение. Для тяжелых расчетов, обработки массивов, копирования больших блоков данных, спектрального анализа и отрисовки больших потоков данных нужно заранее учитывать аппаратное ускорение, если оно оправдано измерениями и сложностью сопровождения.

Принципы:

- сначала правильная доменная модель и тест-пример, затем измерение узких мест, потом оптимизация;
- горячие циклы проектировать без лишних выделений памяти, с переиспользованием буферов и понятным владением данными;
- перед написанием собственной математики проверять существующие наработки `D:\works\OburecGH\sharedUtils\math\uHardwareMath.pas`;
- для SIMD/FFT/aligned memory использовать адаптерный слой, чтобы ядро RecorderLnx не зависело напрямую от конкретной реализации или CPU-инструкций;
- Windows/Linux переносимость сохраняется обязательной: платформенно-зависимое ускорение должно иметь проверяемый fallback;
- графику больших потоков данных в будущем рассматривать через OpenGL/аппаратное ускорение, но UI-графика делается после ядра, примеров и конфигурации.

Аппаратное ускорение не добавляется “на всякий случай” в первый вариант класса. Оно закладывается в архитектурные границы и включается, когда есть понятный объем данных, тест и измеримая польза.
## Документация в коде

Маркер правила: `RLNX_CODE_DOCS_2026_05_25`.

Каждый значимый модуль RecorderLnx должен содержать:

- аннотацию в начале unit: назначение модуля, место в архитектуре, что модуль не должен делать;
- описание назначения публичных классов, функций и процедур;
- описание параметров публичных функций/процедур, если их смысл не очевиден из имени;
- комментарии внутри кода там, где они улучшают читаемость логики, особенно для переходов состояний, потоков, владения данными и обработки ошибок.

Комментарии должны объяснять намерение и ограничения, а не пересказывать очевидную строку кода.
## Библиотеки

Разрешены только зависимости, к которым есть исходный код и понятная лицензия.

Перед добавлением зависимости фиксируем назначение, где лежит исходный код, лицензию, владельца интеграции в RecorderLnx, план замены и классы проекта, которые используют зависимость.

Запрещено добавлять закрытый бинарный компонент как обязательную часть сборки, завязывать ядро на неподконтрольную библиотеку ради удобства UI, смешивать экспериментальный компонент с ядром без адаптерного слоя.

## Lazarus/FPC

- Для нового кода обязательно проверять сборку на Windows и сохранять переносимость под Linux; Linux-специфичный и Windows-специфичный код изолировать в адаптерах.
- Не использовать API одной ОС напрямую в ядре приложения без интерфейса/обертки и записи в карту классов.


- Базовый язык: Object Pascal, Lazarus/FPC.
- Для нового кода использовать единый режим компиляции проекта. Предпочтительно `{$mode objfpc}{$H+}`, если не будет принято другое решение.
- UI строить на LCL.
- Бизнес-логику выносить из форм в отдельные units.
- Стараться сохранять переносимость Windows/Linux там, где это не мешает Windows/Linux-цели.

## Именование

Пока не утверждён отдельный стандарт RecorderLnx, используем AGrav-стиль: локальные переменные `lName`, поля классов `fName`, глобальные переменные `g_Name` только если без них нельзя, интерфейсы `IRecorderCore`, классы `TRecorderCore`.

## Потоки и данные

- UI-поток не выполняет сбор данных, запись файлов, сетевой обмен и тяжёлую обработку.
- Потоки источников публикуют снимки данных, а не изменяемые UI-объекты.
- Для межпоточной передачи использовать очереди, снимки, блокировки с коротким временем удержания.
- В горячих циклах избегать лишнего выделения памяти: буферы создаются заранее и переиспользуются, если это не усложняет код чрезмерно.
- Временные отладочные логи добавляются точечно и удаляются после подтверждения исправления.


## Теги и тестовые данные UI

Маркер правила: `RLNX_TAG_DATA_FLOW_2026_05_25`.

Стандартный путь данных в RecorderLnx: устройства и плагины пишут значения в теги, компоненты формуляров получают обновления через события Recorder/notify и отображают теги по своей внутренней логике. Формы не должны становиться источником доменных данных и не должны содержать функции вида `InitPlaceholderData` с реальной логикой наполнения.

Временные демонстрационные данные для UI, mock-источники и функции-примеры размещаются в `D:\works\OburecGH\Lazarus\Tests\RecorderTests\...`. Если приложение временно подключает такой модуль для раннего UI-каркаса, в шапке unit должно быть явно написано, что это тестовая заглушка до появления core-модели тегов и notify.
## Тест-примеры

Для каждого нового класса нужен пример, который можно выполнить или проверить: консольный тест для не-UI классов, маленькая LCL demo-form для UI-компонентов, mock-источник данных для потоков и событий, golden-file или проверка структуры для сериализации.

Тест-пример должен показывать типовой сценарий использования, а не только проверять одну строку.

Для новых консольных тестов рядом с assert-проверками обязательно выводить наглядный лог результата: что создано, какие ключевые события произошли, какие значения попали в буфер/registry/config, и итоговую строку `RESULT ... passed`. Лог должен писаться не только в консоль, но и в `.log` файл рядом с `.exe`, чтобы результат можно было открыть после запуска из Lazarus или файлового менеджера. Старые тесты специально не переделывать.

## Документация

Каждый значимый класс заносится в реестр: имя класса/интерфейса, unit, назначение, владелец слоя, зависимости, пример/тест, статус. Пока отдельный реестр не создан, записи добавляются в [Карту интерфейсов](./03_Карта_Интерфейсов.md).

## Отображение тревог (Alarms)

Маркер правила: `RLNX_ALARMS_COLOR_DISPLAY`.

Срабатывание любых тревог (alarms) на каналах или системных событиях должно обязательно визуализироваться цветами в любых графических и табличных компонентах пользовательского интерфейса (например, подсветка ячеек формуляров, изменение цвета графиков/осей, мигание индикаторов состояния).

## Кроссплатформенная плагинная система

Маркер правила: `RLNX_CROSSPLATFORM_PLUGINS`.

Для реализации плагинов расширения к RecorderLnx, работающих и собирающихся под Windows и Linux по одной кнопке без изменения кодовой базы проектов, используется технология **динамических библиотек (Shared Libraries / DLL)** с плоским интерфейсом функций **Flat C API** (использование `stdcall`/`cdecl` вызовов, простых типов вроде `Double`, `Integer`, `PChar`/`PAnsiChar` в UTF-8/CP1251 и `record`-структур без динамических массивов LCL). Загрузка плагинов на стороне RecorderLnx осуществляется динамически через функции модуля `DynLibs` (`SafeLoadLibrary`, `GetProcedureAddress`, `FreeLibrary`).
