# RecorderLnx: карта интерфейсов Windows Recorder

Источник: `D:\works\OburecGH\recorder\SharedRUnits\interfaces`.

Эта карта нужна, чтобы при проектировании RecorderLnx не дублировать уже найденные сущности и не терять функционал Windows Recorder. Это не требование переносить COM API один к одному. Это функциональный каталог.

### Уточнение по фабрикам формуляров Recorder

Маркер: `RLNX_RECORDER_FACTORY_USAGE_2026_05_25`.

Проверенные источники:
- `D:\works\OburecGH\recorder\SharedRUnits\interfaces\CFREG.PAS`.
- `D:\works\OburecGH\recorder\SharedRUnits\interfaces\IVFORM.PAS`.
- `D:\works\OburecGH\recorder\SharedRUnits\uRecBasicFactory.pas`.
- `D:\works\OburecGH\recorder\SharedRUnits\uCompMng.pas`.
- `D:\works\OburecGH\recorder\plgEvalFRF\units\uCreateComponents.pas`.
- `D:\works\OburecGH\recorder\plgEvalFRF\forms\uEvalFRFFrm.pas`.

Фактическая модель Recorder:
- `ICustomFormsRegistrator` регистрирует/снимает фабрики (`RegisterFormFactory`, `UnRegisterFormFactory`, `GetFactoriesCount`, `GetFactoryByIndex`).
- `ICustomFormFactory` отвечает за тип компонента/формы: `CreateForm`, `GetFactoryID`, `GetFactoryOwner`, `GetFormTypeName`, `GetFormTypePicture`, `GetDefaultFormSize`, `GetSingleTagFlag`.
- `cCompMng` хранит список фабрик плагина и регистрирует их в UI-сервере Recorder.
- `cRecBasicFactory` хранит детей своего типа в `m_CompList`; `CreateForm` вызывает `doCreateForm`, добавляет объект в `m_CompList`, задает объекту ссылку `m_f := self` и возвращает `IVForm`.
- `ICustomFactInterface.getChild(i, var pIVForm)` дает доступ к детям фабрики по индексу.
- `cRecBasicIFrm` реализует `IVForm`; при уничтожении вызывает `m_f.ExcludeComp(self)`, то есть ребенок уведомляет фабрику и исключается из реестра фабрики.
- `IVForm.Init` создает реальное окно/форму, привязывает его к parent HWND, снимает border и деактивирует до показа.
- Жизненный цикл данных идет через `doStart`, `doStop`, `doUpdateData`, `doRecorderInit`, `Notify`, `ReadSettings/WriteSettings`.

Следствие для RecorderLnx:
- текущий `TRecorderComponentFactory` нужно заменить/расширить до `TRecorderComponentFactoryManager` + фабрик типов, где каждая фабрика ведет реестр своих созданных компонентов;
- компонент должен знать свою фабрику или иметь обратный callback удаления;
- формуляр хранит свои компоненты, но при удалении компонента/формуляра обязан уведомить соответствующую фабрику;
- доступ по индексу нужен на уровне фабрики, не только на уровне страницы;
- первые фабрики RecorderLnx должны проектироваться как аналоги `ICustomFormFactory`, но без COM и Windows-only `HWND` в core.

### Уточнение: базовый Recorder API и framework-надстройка

Маркер: `RLNX_RECORDER_API_VS_FRAMEWORK_2026_05_25`.

`cCompMng`, `cRecBasicFactory`, `cRecBasicIFrm` не являются базовым API Recorder. Это пользовательская/проектная надстройка над интерфейсами Recorder для упрощения разработки плагинов и формуляров.

Базовый контракт Recorder для формуляров и фабрик:
- `ICustomFormsRegistrator`;
- `ICustomFormFactory`;
- `IVForm`.

Надстройка полезна как пример реализации паттерна:
- менеджер фабрик регистрирует фабрики в Recorder;
- фабрика создает детей и может хранить их список;

### Реализация фабрик компонентов RecorderLnx

Маркер: `RLNX_FACTORY_MANAGER_2026_05_25`.

Файл: `D:\works\OburecGH\Lazarus\RecorderLnx\Core\uRecorderFormModel.pas`.

Реализованный слой:
- `TRecorderComponentFactoryBase` — фабрика одного типа модельных компонентов; хранит `TypeId`, `TypeName`, размер по умолчанию, признак `SingleTag` и реестр созданных дочерних компонентов.

- `TRecorderFormPage.DeleteComponent/Destroy` — удаляют компоненты через их фабрику, чтобы фабрика тоже получала lifecycle-уведомление.
