# RecorderLnx: план первой итерации

## Цель первой итерации

Создать минимальное ядро без реальных драйверов, чтобы проверить модель состояний, событий, расширений, тегов, источников данных и тест-примеров. UI допускается только как экран наблюдения/ручного управления уже готовыми core-командами.

После анализа исходников оригинального Recorder в `D:\works\windev-v3.9` первая итерация уточнена: перед тегами и источниками нужен небольшой слой core-сервисов, аналогичный полезным идеям `IRecorder`, `CPluginsMan`, `ICustomButtonsToolBar`, `IProcessingManager`, но без COM/MFC/HWND в ядре.

## Итерация 1: состояние приложения

Первый реализуемый класс: `TRecorderStateMachine`.

Требования: состояния `Stop`, `PreviewArmed`, `Preview`, `RecordArmed`, `Record`; проверка допустимости переходов; событие изменения состояния; запрет конфигурации вне `Stop`; текстовое описание текущего состояния.

Статус: реализовано в `Core\uRecorderStateMachine.pas`, проверено консольным примером и сборкой проекта.

## Итерация 2: минимальные core-сервисы расширяемости

Классы/units:

- [x] `TRecorderEventBus` — типизированные события вместо числовых `PN_*`.
- [x] `TRecorderActionRegistry` — регистрация команд, которые позже может показать toolbar/menu/hotkeys.
- [x] `TRecorderExtensionManager` — учет статических расширений первой версии и единый lifecycle.

Задача этой итерации — дать будущим тегам, формулярам, плагинам и processing общий язык событий и команд. Это маленький слой, но он предотвращает будущие прямые связи UI с core и дублирование notify-механизмов.

Пример/тест: создать event bus, подписать обработчик, отправить `rceDataUpdated`; зарегистрировать action, вызвать его; создать mock extension и проверить порядок `Initialize/RegisterServices/Start/Stop/Close`.

Статус: реализовано в `Core\uRecorderCoreServices.pas`, проверено тестом `Tests\RecorderTests\CoreServices\RecorderCoreServicesTest.lpi`.

## Итерация 3: теги и сигнальный буфер

Классы: `TTag`, `TTagRegistry`, `TSignalBuffer`.

Пример/тест: создать 3 тега; добавить данные в буфер; получить снимок; проверить поиск по имени и id.

Статус: реализовано в `Core\uRecorderTags.pas`. Тест-пример `Tests\RecorderTests\Tags\RecorderTagsTest.lpi` создает `MemTag`, публикует значения через registry, печатает лог `rceDataUpdated` и snapshot кольцевого буфера.

## Итерация 4: mock-источник данных

Классы: `IDataSource`, `TMockSineDataSource`, `TDataSourceThread` или безопасный прототип без отдельного thread на первом шаге.

Пример/тест: источник генерирует синус/счётчик с `UpdateTime`; публикует `TDataFrame`; registry обновляет теги; событие `OnDataUpdated` вызывается ожидаемое число раз.

Статус: первый прототип реализован в `Core\uRecorderDataSources.pas`. Есть `IRecorderDataSource`, `TRecorderDataSourceBase`, `TMockSineDataSource`, `TRecorderDataSourceThread` и `TRecorderDataSourceManager`; источник создает/подключает тег, по ручному `Tick` публикует значения через `TRecorderTagRegistry`, thread-runner запускает один источник с его `UpdateTimeMs`, а manager запускает/останавливает набор источников как группу через `Terminate/WaitFor`. Тест-пример `Tests\RecorderTests\DataSources\RecorderDataSourcesTest.lpi` пишет наглядный `RecorderDataSourcesTest.log` рядом с `.exe`: ручные тики, одиночный thread-runner и manager на два источника.

## Итерация 6: минимальный UI данных

- Главное окно Lazarus.
- Кнопки `Stop`, `View`, `Record`.
- Дерево источников/тегов.
- Один простой формуляр отображения текущих значений.

Пример/тест: запуск mock-источника; отображение значений без прямого доступа worker thread к UI; остановка без зависания.

Статус подготовки: реализован core-мост `TRecorderEventSnapshotQueue` в `Core\uRecorderEventQueue.pas`. Он подписывается на `TRecorderEventBus`, копирует события источников данных в потокобезопасную очередь и проверен тестом-примером `Tests\RecorderTests\EventQueue\RecorderEventQueueTest.lpi` с логом `RecorderEventQueueTest.log` рядом с `.exe`.

Статус UI: главная форма `UI\uMainForm.pas` подключает `TRecorderEventBus`, `TRecorderTagRegistry`, `TRecorderDataSourceManager` и `TRecorderEventSnapshotQueue`. В режимах `View`/`Record` запускается отладочный источник `debug.memtag -> MemTag`; UI-таймер вычитывает очередь и обновляет цифровой формуляр/список тегов только из UI thread.

## Итерация 7: запись данных

- Минимальный writer в текстовый/CSV/бинарный временный формат.
- Flush/close при `Record -> View` и `Record -> Stop`.
- Метаданные кадра записи.

Формат записи окончательно не утверждать до анализа совместимости с существующим Recorder/MERA.

Статус ядра: реализован `Core\uRecorderDataStorage.pas` с `TRecorderRecordFrameManager` и `TRecorderCsvTagWriter`. Manager создает кадры записи `0001`, `0002`, ... в корневом каталоге записи и пишет `frame.ini`; writer пишет временный `tags.csv`. Тест-пример `Tests\RecorderTests\Storage\RecorderStorageTest.lpi` создает два кадра записи, выводит содержимое `frame.ini`/`tags.csv` в лог `RecorderStorageTest.log` рядом с `.exe`.

## Обновление плана: система времени

Маркер: `RLNX_TIME_SYSTEM_2026_05_26`.

Статус времени: реализован `Core\uRecorderTimeSystem.pas` как первый слой системы времени RecorderLnx. Главная форма отображает время транспаранта через `TRecorderTimeSystem.Snapshot`, а не вручную. В текущем шаге поддержаны источники PC/elapsed/tag-time/UTS-time на уровне модели; отдельный поток отображения остается следующим архитектурным шагом.

Проверка времени: `Tests\RecorderTests\TimeSystem\RecorderTimeSystemTest.lpi` собирается, запускается и пишет `RecorderTimeSystemTest.log` рядом с `.exe`.
