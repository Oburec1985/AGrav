# Архитектура локальной памяти ИИ-ассистента

Система памяти ассистента Antigravity делится на два уровня:
1. **Оперативная память (Локальный кэш проекта)**.
2. **Долговременная (семантическая) память (MemoryDB)**.

---

## 1. Оперативная память (Проектный кэш)

Реализуется в виде файлов `.md` в папке `cach/` каждого проекта. 

- **plan.md**: Текущий чек-лист задач.
- **notes_last_state.md**: Фиксация выполненного, Memory Log промптов и измененных файлов.
- **notes_<тема>.md**: Анализ конкретных модулей и архитектурные решения.

**Принцип работы**: ИИ считывает эти файлы напрямую при старте сессии, обеспечивая мгновенный и точный контекст последних шагов.

---

## 2. Долговременная память (MemoryDB)

Реализуется через локальный Python MCP-сервер, общающийся с IDE по протоколу JSON-RPC.

```text
+-----------------------+
|  Antigravity AI LLM   |
+-----------+-----------+
            |
            | (stdin / stdout - JSON-RPC)
            v
+-----------+-----------+
|    MCP Server Process |
|      (src/main.py)    |
+-----+-----------+-----+
      |           |
      |           | (Генерация векторов)
      |           v
      |     +-----+-------------+
      |     |  FastEmbed (ONNX) | <--- [model_cache/.../model_optimized.onnx] (~220 МБ)
      |     +-------------------+
      |
      | (Вставка / Поиск точек)
      v
+-----+-----------------+
| Qdrant Client (Local) |
+-----------+-----------+
      |           |
      |           | (Локальный кэш векторов)
      |           v
      |     +-----+-------------+
      |     |  memory_store.db/ | (В .gitignore, пересоздается автоматически)
      |     +-------------------+
      |
      | (Синхронизация при старте)
      v
+-----+-----------------+
|    data/records/*.json| (В Git! Исходный код правды, по одному файлу на факт)
+-----------------------+
```

### Структура хранения знаний

Хранение знаний разделено на две части для удобства версионирования в Git:

1. **Текстовые JSON-файлы (`data/records/<uuid>.json`)**:
   - **Что это?** Это основной источник правды (Single Source of Truth). Каждый сохраненный факт лежит в отдельном текстовом файле в формате JSON.
   - **Содержимое**: JSON содержит `id` (UUID), `fact` (текст факта), `tags` (метки), `project_context` (контекст проекта) и `created_at` (дата создания).
   - **Зачем?** Они легковесные, отлично читаются человеком, версионируются в Git (можно смотреть историю изменений каждого факта) и быстро синхронизируются с GitHub.
   
2. **Локальный кэш векторов Qdrant (`data/memory_store.db/`)**:
   - **Что это?** Это локальная папка Qdrant-хранилища (работает через SQLite + NumPy под капотом). Внутри находится файл `storage.sqlite` и служебные файлы.
   - **Зачем?** В ней хранятся сгенерированные векторные эмбеддинги для быстрого семантического (смыслового) поиска.
   - **Нужен ли этот файл в Git?** **Нет.** Этот каталог добавлен в `.gitignore`. Если удалить эту папку, система автоматически восстановит её при следующем запуске MCP-сервера, перечитав все JSON-файлы из `data/records/` и пересчитав эмбеддинги.

3. **Локальный кэш модели ONNX (`model_cache/`)**:
   - **Что за файл `model_optimized.onnx` (~220 МБ)?**
     Это скомпилированная и оптимизированная нейросетевая модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` в формате ONNX.
     - Она используется библиотекой `fastembed` для локальной генерации 384-мерных векторов из текста на лету (без обращений к внешним серверам).
     - Она весит ~220 МБ, так как содержит веса обученной нейросети для понимания русского и английского языков.
     - Этот каталог также добавлен в `.gitignore` и не отправляется на GitHub. При первой установке на новом устройстве модель скачивается автоматически.

## 3. Процесс обновления и удаления информации

Синхронизация локального кэша векторов Qdrant и файлов на диске происходит автоматически при инициализации `MemoryDatabase` (при старте MCP-сервера):

### Корректировка заметок
Если вы измените существующий файл `.json` в `data/records/` (например, исправите опечатку, дополните факт или измените теги) и перезапустите сервер:
1. Система сравнит значения полей JSON на диске с тем, что сохранено в Qdrant.
2. Обнаружив несовпадение, она перевычислит эмбеддинг для обновленного текста и обновит запись в Qdrant.

### Удаление информации
- **Через инструмент**: При вызове инструмента `delete_memory_fact(uuid)` сервер удаляет соответствующий JSON-файл с диска (`data/records/<uuid>.json`) и удаляет запись из Qdrant.
- **Вручную**: Если вы удалите JSON-файл вручную из папки `data/records/` и перезапустите сервер, механизм синхронизации обнаружит отсутствие файла для этого ID на диске и автоматически удалит соответствующий вектор из базы данных Qdrant.

### Преимущества локального хранения:
1. **100% Автономность**: Не зависит от интернет-соединения или внешних облачных провайдеров.
2. **Нулевой оверхед по портам**: Qdrant в `local` режиме открывает файл напрямую из Python-процесса, не занимая сетевых портов и не конфликтуя с локальными сервисами (например, PostgreSQL или 3X-UI).
3. **Безопасность**: Личные данные, исходный код и правила не отправляются на сторонние сервера для построения эмбеддингов или векторного поиска.
4. **Легковесность**: Использование `fastembed` на базе `onnxruntime` исключает тяжелые зависимости вроде `torch` или `transformers`. ONNX модель весит около 220 МБ и генерирует вектор размерностью 384 за считанные миллисекунды на стандартном CPU.

## 4. Оптимизация памяти и интеграция с Obsidian

Для поддержания базы знаний в актуальном состоянии и предотвращения её засорения используется разделение памяти и связывание заметок.

### 4.1. Разделение памяти (Быстрая vs. Долговременная)

1. **Текущие быстрые факты (Оперативная память)**:
   - **Где хранить**: В локальных файлах чек-листов и текущего состояния проекта (`cach/plan.md`, `cach/notes_last_state.md`).
   - **Что хранить**: Мелкие операционные детали ("поправил баг в строке 15", "нужно переименовать переменную X в Y", "сейчас работаю над функцией Z").
   - **Жизненный цикл**: Очищаются или архивируются после завершения задачи.
2. **Долговременная семантическая память (MemoryDB)**:
   - **Где хранить**: В `data/records/` (в виде JSON-файлов для Git) и векторном Qdrant (`memory_store.db/`).
   - **Что хранить**: Глобальные выводы, особенности технологий, архитектурные решения и правила, применимые ко всему проекту или смежным проектам (например: "в Lazarus Caption требует CP1251ToUTF8", "в многопоточности Delphi не выделять память в потоке").
   - **Жизненный цикл**: Постоянное хранение, периодическая очистка утилитой.

### 4.2. Интеграция с Obsidian и предотвращение дублирования

Чтобы избежать дублирования информации (когда один и тот же текст лежит и в Obsidian, и в JSON-файле MemoryDB), используется связывание:

1. **Связывание через YAML Frontmatter**:
   Каждая проиндексированная заметка Obsidian в самом начале содержит стандартизированный YAML-блок:
   ```yaml
   ---
   memory_id: 02a3170e-9437-422e-8f34-f45398be8f95
   indexed_at: 2026-06-09T14:30:00
   ---
   ```
2. **Поведение LLM при работе с Obsidian**:
   - Перед индексацией файла LLM проверяет наличие поля `memory_id` в YAML-блоке.
   - Если `memory_id` есть, файл **уже проиндексирован**. LLM не создает дубликатов.
   - Если `memory_id` отсутствует, LLM делает саммари/выжимку ключевых мыслей файла, вызывает инструмент `save_memory_fact`, получает новый UUID и прописывает его в YAML-блок в начало заметки.
3. **Формат записи в MemoryDB**:
   Вместо копирования всего текста Obsidian заметки в базу данных, в JSON-файле факта сохраняется сжатая выжимка правил с обязательной ссылкой на исходный файл:
   ```json
   {
     "id": "02a3170e-9437-422e-8f34-f45398be8f95",
     "fact": "В проекте RecorderLnx при кодировании файлов в cp1251 русские строки для LCL компонентов требуют CP1251ToUTF8.",
     "tags": ["lazarus", "encoding", "cp1251"],
     "project_context": "RecorderLnx",
     "source_file": "20_Проекты/MemoryDB/docs/README.md",
     "created_at": "2026-06-09T14:30:00"
   }
   ```
   Это решает проблему дублирования и связывает семантическую базу с файловой структурой Obsidian.
