# RLM — выполнение и поиск

**Для агентов (Cursor/Codex):** этот файл — основной протокол.  
**Теория + Python:** [reference.md](reference.md)  
**Архитектура:** [Recursive_Language_Models.md](../../../10_Работа/Программирование/Методологии/Recursive_Language_Models.md)  
**Cursor-копия:** `~/.cursor/skills/rlm-search/SKILL.md`

## Когда использовать

- Сверхдлинный контекст: логи, vault, порт Delphi→Lazarus, 50+ файлов.
- Многошаговая отладка с гипотезами (см. `errors/` в проекте).
- Сверка цепочки «диалог → переменные → BIOS» с оригиналом Recorder.
- Задача не решается одним grep/read.

## Принцип

Не читать всё в промпт. Итерации: **гипотеза → узкий поиск → факт → обновление состояния**. Подзадачи — рекурсивно (дочерний агент / `rlm_query`).

## Qdrant-first: оригинальный Recorder

При работе с `D:\works\windev-v3.9` сначала вызывать
`search_original_recorder_sources` с описанием поведения и известными
символами. Запрашивать 5–12 чанков, затем проверять релевантные результаты в
оригинальном файле по возвращённому диапазону строк и трассировать точные
символы/вызовы через `rg`. Эмбеддинги служат навигацией, а не окончательным
доказательством. Индексирование работает только на чтение и никогда не должно
изменять дерево оригинального Recorder.

## API → инструменты

| RLM | Агент / Инструменты |
|-----|---------------------|
| `context` | Пути, репо; читать выборочно |
| REPL-цикл | grep, `search_vault_notes` (семантический поиск), read, shell |
| `llm_query` | Анализ одного фрагмента |
| `rlm_query` | Subagent / Task с узким промптом |
| `answer["ready"]` | Чеклист «задание закрыто» |
| `sync` | `sync_vault_notes` (обновление индекса заметок после правок) |

## Алгоритм задачи

1. **Цель и критерий готовности** — одним абзацем.
2. **Декомпозиция** — 3–7 подвопросов.
3. **Цикл (≤10 шагов):** гипотеза → поиск → факт (файл:строка) → таблица находок.
4. **Рекурсия:** изолированная подзадача → дочерний агент (глубина ≤3).
5. **Завершение:** итог + самопроверка по исходному заданию.

## Ограничения

- Не повторять отклонённые гипотезы без новых данных.
- Читать `errors/*.md` до новых проверок.
- Без деструктивных команд без явного запроса.

## Пример (MIC-140)

| Шаг | Действие |

## Сетевая отладка приборов

Если задача касается сетевого прибора или протокола, перед изменением кода делай контрольный план захвата:

1. Определи признаки трафика устройства: IP, порт, командные байты, заголовок кадра, длину, CRC/checksum, номер канала, id модуля или известный шаблон MIC140.
2. Запусти сниффер с узким фильтром по этим признакам. Сохраняй сырой `.pcapng` и декодированный текстовый/CSV дамп.
3. По возможности сначала сними эталон с известной рабочей программы. Для MIC140 запусти оригинальный Windows Recorder, попроси пользователя несколько раз нажать просмотр/опрос, сохрани этот обмен как reference dump.
4. Сними дамп новой реализации при той же последовательности действий.
5. Сравни порядок пакетов, тайминги, размеры запросов/ответов, command id, payload, checksum, повторы и жизненный цикл соединения.
6. Клади дампы в проектную диагностическую папку (`captures/`, `dumps/`, `cach/` или `errors/`) с датой, сценарием, фильтром, адресом прибора и версией программы.

Имена файлов:

```text
captures/YYYY-MM-DD_mic140_original_recorder_view_01.pcapng
captures/YYYY-MM-DD_mic140_original_recorder_view_01.txt
captures/YYYY-MM-DD_mic140_recorderlnx_view_01.pcapng
captures/YYYY-MM-DD_mic140_compare_notes.md
```
